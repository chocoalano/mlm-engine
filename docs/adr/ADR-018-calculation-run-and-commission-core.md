# ADR-018: Commissions are calculated by registered strategies in audited, snapshot-consistent runs, and paid only through the ledger

## Status

Accepted — Phase 2.8.

## Context

Plans need commissions: amounts members earn over a period, computed by rules that differ from plan to plan. The package has versioned plan definitions (ADR-014), qualification (ADR-015), ranks (ADR-016) and a balanced, immutable ledger (ADR-017). What it lacked is the generic core every compensation rule will share: how a calculation is chosen, run, made reproducible and auditable, how its results are reviewed, and how they become money. No concrete compensation rule is decided yet, so the core must know none.

## Decision

- **One built-in component, no built-in strategy.** `commission.strategy` is a package-owned plan component driver, registered like `rank.ladder`. Its parameters are exactly `strategy` (a registry key), `currency`, `source_account` (a system ledger account key) and `parameters` (the strategy's own inert JSON object); anything missing, unknown or malformed blocks `markValidated()`, while a draft may hold it. The strategy itself is trusted code in the `CommissionStrategyRegistry` — an application singleton filled at boot through `register()`, refusing invalid, duplicate and unknown keys, never replacing a registration. The package registers no strategy: every concrete compensation rule arrives as a strategy of its own. There is no formula language, and the engine contains no rule-specific branch.
- **Strategies validate, then calculate; they never write.** `validate(CommissionStrategyDefinition)` judges the component's parameters and rules — read-only data naming its version — without business data, when the version is validated and again before each calculation. `calculate(CommissionCalculationContext)` reads through the package's models and read services — metrics, qualification, rank — and returns candidates. How a component's rules combine is the strategy's decision. Strategies must not insert commissions, post to the ledger, open wallets or change definitions: a contract for trusted code, not a sandbox.
- **Explicit, closed, validated.** `CalculationEngine::calculate(PlanComponent, CalculationContext)` calculates the one stored component the caller passes — never an active plan, version or every component — over a closed range `[from, until)`: both bounds required, `from` first, normalised to the application's timezone and whole seconds. The component must be a `commission.strategy` of a validated version — validated, published, active, superseded or archived — never a draft, and is not swapped for the active version's. Component, version, plan, program and source account are re-read.
- **The source account is resolved, never opened, and captured.** Before the strategy runs, the component's `source_account` must be an existing system account of the program in the component's currency; a missing key, another program's or currency's account, or a wallet's account stops the run. Its id is stored on the run, and every commission of the run is posted from exactly that account.
- **Only successful runs are stored.** A run is synchronous: the strategy's candidates are all collected and checked — then the run and every commission are inserted in one transaction. Any failure — the strategy throwing, a bad candidate at any position, a write failing — leaves no run and no commission. There is no queued, running or failed state; a stored run is a complete result.
- **Idempotent without recalculation.** The caller's idempotency key identifies a run within its program. A request under a used key returns the stored run — without running the strategy, even if the data has changed since — if it names the same component and range (and so the same version, strategy, currency and source account); otherwise `ConflictingCalculationReplay`. A new calculation needs a new key. The unique key is the concurrency backstop: of two racing identical requests one stores the run and the other returns it; of two conflicting ones, the other is refused.
- **One read snapshot per run, owned by the engine.** The calculation and the stored result share one transaction, and every read inside it sees one snapshot: REPEATABLE READ on MySQL, MariaDB and PostgreSQL — set for that transaction only, before its first read — and a plain transaction on SQLite, which reads one consistent state. So a strategy may compose several reads — members, metrics, qualification — and they agree, even while other sessions commit. A calculation refuses to start inside a caller's transaction, whose isolation and snapshot would already be decided. Real concurrent tests on MySQL and PostgreSQL prove the snapshot: a strategy reads, another session commits more volume and a new member, and the strategy's second read still sees the first — even under a session whose default isolation is READ COMMITTED.
- **Candidates.** A `CommissionCandidate` names a key — 1–191 characters, unique within the run; a duplicate fails the run rather than being merged — a member, a strictly positive exact amount that fits one ledger posting (never split, never zero, never negative: corrections are reversals), an explicit earned-at moment, and a trace. The member is re-read and must belong to the run's program. Candidates are stored in key order, whatever order the strategy yields them in.
- **Traces are inert, canonical and bounded.** A trace holds strings, integers, booleans, null, lists and objects with text keys — no floats (numbers are exact strings), objects, closures or resources — at most 16 levels, 10,000 values and 64 KiB of JSON. Object keys are sorted recursively before storage and again when read, so no database's JSON key order is relied on.
- **A lifecycle prefix, one commission at a time.** A stored commission is CALCULATED; `CommissionLifecycle` moves it to PENDING, then APPROVED, and can CANCEL it at any of those — moving no money, and ending its life. Only `CommissionPoster` moves it to POSTED, and from POSTED to REVERSED. No other transition exists; there is no batch API. Every move locks the stored row and decides from the stored status. HELD, AVAILABLE and PAID are deliberately absent: hold and release, availability and payout rules are not defined, and posting to a wallet is not payout eligibility. What a run calculated — member, amount, currency, earned-at, trace — never changes; runs and commissions are read-only through Eloquent.
- **Explicit approval before money moves.** Calculating opens no wallet, approves nothing and moves no money; posting a CALCULATED or PENDING commission is refused. This keeps room for later review workflows.
- **Posting only through the ledger.** `CommissionPoster::post()` locks an APPROVED commission, opens its member's wallet if need be, and posts one balanced transaction through `LedgerRecorder::post()`: the run's source account debited and the wallet credited by exactly the commission's amount, occurring at the commission's earned-at moment, of type and source type `commission`, source id the commission's id, idempotency key `commission.post.<id>`. The status, its moment and the ledger transaction id are stored in the same transaction: all of it or none. One commission maps to one posting transaction. Posting a POSTED commission returns it after checking its stored transaction is exactly the one posting it; racing posts move the money once.
- **Reversal through the ledger.** `CommissionPoster::reverse()` locks a POSTED commission and reverses its ledger transaction through `LedgerRecorder::reverse()`, at a moment the caller gives — a later financial event, not the earned-at — under `commission.reverse.<id>`, storing REVERSED, its moment and the reversal's id together. The original ledger transaction is untouched. Reversing again at the same moment returns the commission; at another moment it is refused. Racing reversals reverse once.

## Consequences

- Any compensation rule can now be added as a registered strategy without changing the engine, the run, the lifecycle or the ledger, and every result it produces is reproducible — by replaying the stored run — and traceable to its version, component, strategy, range, source account and ledger transactions.
- A run holds its snapshot transaction for the whole calculation; long calculations hold it longer. A calculation cannot join a caller's transaction.
- A strategy's reads are only as consistent as the package's connection: reads through another connection are outside the snapshot.
- Held, available and paid commissions, payouts, persisted calculation periods, batch review, fees, taxes and rounding policies are later phases, which extend this lifecycle rather than replace it.
