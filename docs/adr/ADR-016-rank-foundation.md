# ADR-016: A rank ladder is a plan component whose rules are its ranks, and its rank is derived, never stored

## Status

Accepted — Phase 2.6.

## Context

Plans need ranks: an ordered set of titles — bronze, silver, gold — each with its own requirement, and the answer to "which rank does this member reach over this range?". Plan definitions already hold versioned, validated, immutable components and rules in a safe rule language (ADR-014), and qualification already evaluates one stored rule exactly, with a complete trace (ADR-015). What a rank *means* over time — when it is awarded, whether it can be lost, whether it is kept per period, whether it can be corrected — is not decided yet.

## Decision

- **No rank table.** A rank ladder is a plan component with the driver `rank.ladder`; each of its rules is one rank. There is no `mlm_ranks`, `mlm_plan_ranks`, `mlm_member_ranks` or rank result table, no rank column on members, and no migration. Ladders are drafted with `PlanDefinitionEditor`, validated with the version, and copied into new drafts by `PlanDefinitionCloner`, as any component is: there is no rank editor or rank cloner.
- **One rule is one rank.** The rule's key is the rank's stable key, its name the rank's display name — not unique, not an identity — its position the rank's place, and its definition the rank's requirement. No other rank identifier, name or order is stored.
- **A larger position is a higher rank.** Positions are unique within a ladder, so the order is the plan's own and never falls back on ids; gaps — 10, 50, 999 — are fine.
- **The built-in driver.** `RankLadderDriver` is the package's first component driver, registered under `rank.ladder` by the service provider through the same `PlanComponentDriverRegistry::register()` applications use; an application cannot register another under that key, and registers its own drivers beside it. It checks, when the version is validated, that the ladder takes no parameters (none is defined yet — no strategy, fallback, demotion or promotion setting), holds at least one rank, and has no two ranks at one position. Rules, metrics and their parameters are checked by the generic validator, not again. A draft may hold an empty or ambiguous ladder while it is edited; `markValidated()` refuses it with `InvalidPlanDefinition`, and the version stays a draft. There is no database constraint: rule positions are generic to all components.
- **Explicit ladder selection.** `RankEngine::evaluate(PlanComponent $ladder, RankContext $context)` evaluates the stored ladder the caller passes. It never selects a plan, an active version or a ladder, and never merges two ladders of a version. A component of another driver is refused, not answered as unranked.
- **Validated versions only, from stored state.** As for qualification: a draft's ladder is refused; a ladder of any validated version — validated, published, active, superseded, archived — can be evaluated, and is never swapped for the active version's. The component, its version, plan, program and ranks, and the member are re-read; the member must belong to the ladder's program.
- **Ranks are qualified, one by one, through qualification.** `RankEngine` depends on `QualificationEngine` alone: each rank's rule is evaluated by it, for the stored member, with a `QualificationContext` over the `RankContext`'s `[from, until)` range — the same range for every rank. The rank engine evaluates no condition, compares no value, resolves no metric and knows nothing of genealogy or reversals; custom metrics, network history and reversal attribution come through qualification and the metrics unchanged. No qualification or metric result is cached across ranks, even when ranks share conditions.
- **Every rank is evaluated, lowest position first.** Nothing stops once a rank qualifies or fails, so the decision explains the whole ladder.
- **Ranks are independent; the highest qualifying position wins.** A higher rank does not require the lower ones: a member who meets gold's requirement and not silver's is gold. A plan that wants a higher rank to include a lower one's requirements writes them into the higher rank's rule. No rank refers to another's result.
- **None qualifying is a decision.** When every rank is evaluated and none qualifies, the selected rank is null: unranked under this ladder, version and range — not an error.
- **Technical failure is not a rank.** A wrong driver, a draft, another program, a missing record, a stored ladder validation would refuse — empty, positions shared, parameters present, only raw writes produce it — or a rank whose qualification throws, fails the whole evaluation with `RankEvaluationException`, naming version, component, rank key and position, keeping the cause, and never parameter values. No decision is returned: no lower rank, no null, no partial result with a warning. The achieved rank is unknown, not lower.
- **The decision.** `RankDecision` is plain data: the ids and codes of program, plan and member, the version's id and number, the component's key and name, the range, the `SelectedRank` (key, name, position) or null, and every rank as a `RankCandidateDecision` — key, name, position, qualified, and its qualification trace, reused as it is, with no second trace format — lowest position first. Identities are not repeated per rank. There is no evaluation time: the same stored data and context give the same `toArray()`.
- **Derived, never stored.** Evaluation writes nothing. A historical rank is re-derived from a historical version's ladder and a historical range.

## Consequences

- Any validated ladder can be evaluated for any member of its program over any range, now or later, with the reason for every rank — the rank a commission rule may later rely on is reproducible.
- Evaluating a ladder costs one qualification per rank and one metric resolution per condition, shared conditions included. Worth measuring before adding a cache with explicit semantics.
- `RankDecision` is deterministic for unchanged persisted state, but Phase 2.6 does not establish a database-wide read snapshot: its qualifications, and their metric reads, are separate queries, and a write committed during an evaluation may be visible to some ranks and not others. Snapshot and calculation-run consistency belong to a later orchestration layer.
- Nothing records when a rank was reached. Rank persistence, current rank, rank history and achievements, promotion, demotion, maintenance, grace periods, expiry, rank-based metrics and calculation periods need a deliberate lifecycle design first, and are later phases.
