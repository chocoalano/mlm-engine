# ADR-014: A plan version's definition is relational, driver-keyed configuration with rules in a safe rule language

## Status

Accepted — Phase 2.4. Amended in Phase 2.5: the rules are now evaluated, one chosen rule at a time (ADR-015).

## Context

A plan version (ADR-004, ADR-005) had a lifecycle but no content. Plans need versioned, auditable business configuration: which parts a plan has — qualification, ranks, pools, an application's own — and the conditions those parts test. Later phases will evaluate that configuration; before they can, it must be storable, checkable and immutable once checked.

Configuration lives in the database and is edited by people, so it must never become a way to run code: no class names, closures, serialized objects, SQL, expressions or scripts may be stored and later executed.

## Decision

- **A version owns its whole definition.** Components belong to a `PlanVersion`, rules to a component. Nothing is attached to `Plan`, `Program` or `Member`. The definition is two relational tables, not one JSON document.
- **Plan components** (`mlm_plan_components`, migration 000011): a ULID, the version, a machine `key` unique per version, a `driver` key, a human `name`, a `parameters` JSON object and a `position`. The same key may appear in other versions, which is what cloning relies on.
- **Drivers are trusted code selected by key.** The component stores the driver's key — 1–100 lowercase letters, digits, `.`, `-` or `_` — never a class name. The key finds an already-registered `PlanComponentDriver` in the `PlanComponentDriverRegistry`, an application singleton filled at boot through `register()`, like `MetricRegistry` (ADR-011). An invalid key is refused, a second registration of a key is refused rather than replacing the first, and an unknown key fails. The package registers no driver of its own: the first real ones arrive with the business domains that need them.
- **A driver only validates, for now.** `validate(PlanComponentDefinition)` receives the complete component as read-only data — key, driver, name, parameters, position and its parsed rules in order — never a model, and may refuse it. There is no `execute()`: what a component does belongs to the contracts of later phases.
- **Parameters are inert JSON data.** A JSON object — strings, numbers, booleans, null, lists and objects, nested at most 32 deep — stored with its keys in canonical order and read back the same way, whichever database stored it. Objects, closures, resources, enums, non-finite numbers and invalid UTF-8 are refused, not converted. What the values mean is the driver's business; nothing reads them as code.
- **Plan rules** (`mlm_plan_rules`, migration 000012): a ULID, the component, a machine `key` unique per component, a `name`, a `definition` and a `position`. A rule is the relational audit boundary: a later trace can say which version, component and rule decided something, and a condition's place in the tree (`root.children[1]`) identifies it within its rule. Conditions have no ids or tables of their own.
- **The rule language.** A rule's definition is a tree, stored as JSON because its shape is nested and varies with the configuration — the same reasoning as parameters: identity relational, flexible structure JSON. The JSON is governed by a strict schema:
  - The root is always a group. A group is `{"type": "group", "match": "all" | "any", "children": [...]}` with at least one child; `all` will mean every child holds, `any` at least one.
  - A condition is `{"type": "condition", "metric": key, "parameters": {...}, "operator": op, "operands": [...]}`.
  - Operators: `!=`, `>`, `>=`, `<`, `<=` take exactly one operand; `in` and `not_in` one or more; `between` exactly two, lower bound first, **both bounds included**. There is no equality, pattern, `LIKE`, function or arithmetic: adding one is a deliberate amendment.
  - Operands are exact decimals — what a `MetricValue` holds, at most six places — stored as canonical strings (`"100"`, `"-25.5"`). A float is refused; nothing is rounded.
  - Every node has exactly its fields: an unknown field, a missing field, an unknown type, combinator or operator is refused, never ignored.
  - Defensive limits: the root is at depth 1 and no node lies deeper than 16; at most 500 nodes in a tree; at most 100 operands in a condition; stored JSON is parsed at most 128 levels deep. They guard against pathological input and are not configuration.
  - `RuleDefinition`, `RuleGroup` and `MetricCondition` build, parse (`fromArray`, `fromJson`) and serialise (`toArray`, `toJson`) it canonically; a stored rule is read back through the same parser, and stored JSON outside the language is refused rather than read as an empty or partial rule. Code-like text in a key, operator or operand is refused by the shape those fields allow, not by looking for suspicious words; text inside parameters is kept as plain data.
- **Metric references are checked without resolving.** A condition names a metric key and its parameters. A metric may be named only if it implements the opt-in `PlanConfigurableMetric`, whose `validatePlanParameters()` judges parameters without reading data. `Metric` itself is unchanged, so every existing metric keeps resolving through `MetricEngine`; only its use in a plan rule requires the new contract. `member.volume`, `sponsor.network.volume` and `placement.network.volume` implement it through the same code path their `resolve()` uses, so plan validation and resolution accept and refuse exactly the same parameters.
- **Validation guards the transition.** `markValidated()` locks the version row, requires a draft, runs `PlanDefinitionValidator` over the whole stored definition and only then marks the version validated — one transaction. The validator reads every component and rule in order and requires: well-formed keys, names and parameters; a registered driver; every rule in the language; every named metric registered, plan-configurable and accepting its parameters; and the driver's own approval. Its errors name the version, component, rule, condition path and metric, never parameter values. A failure leaves the version a draft, `validated_at` null, the definition unchanged. An empty definition is valid, so existing versions and flows are unaffected. No member is involved and no metric value is computed.
- **Drafts only, one writer.** `PlanDefinitionEditor` adds, updates and removes components and rules. Every operation re-reads the version, locks its row — the row `markValidated()` locks — and refuses with `PlanVersionNotMutable` unless it is still a draft, whatever an instance in memory says. So an edit and a validation cannot interleave: either the edit commits first and validation sees it, or validation commits first and the edit is refused. The editor checks shape, not existence: a draft may name a driver or metric that is not registered yet. Keys are identities and are not renamed; positions default to after the last one and read by position, then id. The models are read-only through Eloquent — creating, updating or deleting a component or rule through them is refused, and nothing is mass assignable — and the editor writes through the query builder.
- **Changes after validation are new drafts.** From `validated` on — `published`, `active`, `superseded`, `archived` — nothing in a definition changes. `PlanDefinitionCloner::cloneToNewDraft()` locks the plan, then the source, allocates the next draft through the lifecycle, and copies every component and rule — keys, names, drivers, parameters, definitions, positions — under new ids, in one transaction. No status or timestamp is copied. The copy is inert: no driver runs, so a definition naming a driver that is not registered today still copies, and cannot be validated until it is. Parameters and rules are re-read through their parsers on the way, so stored data outside them — only raw writes produce it — stops the copy, and nothing of it remains.
- **Ownership.** Components cascade with their version, rules with their component: only a draft can be deleted through the supported API, and its definition goes with it. Plan and program ownership is unchanged.
- **Identifiers compare exactly.** Component and rule keys and driver keys use the binary collation on MySQL and MariaDB, as every identifier does (ADR-002); names do not.
- **No business configuration in `config/mlm.php`.** Drivers, operators and thresholds are not settings.

## Consequences

- A plan version can now hold real, auditable configuration, and that configuration is immutable from the moment it is validated.
- Nothing is evaluated: there is no rule evaluator, qualification, rank or commission, and no method answers true or false for a member. The language fixes what a future evaluator must support — including `between` being inclusive — without committing to how. Since Phase 2.5 `QualificationEngine` evaluates one stored rule of a validated version (ADR-015); ranks and commission are still absent.
- Periods are not part of the language: a metric's period will come from the evaluation context, not from a rule.
- Raw SQL can still write anything to these tables, bypassing the editor, the lifecycle and every check, as for every other table (ADR-005, ADR-007). Reading such data through the models, the validator or the cloner fails loudly instead of misreading it.
- An application that relied on `Metric` alone keeps working; to name its metric in a plan rule it opts into `PlanConfigurableMetric`.
