# ADR-017: Money moves only as balanced, immutable ledger transactions; a balance is derived, never stored

## Status

Accepted — Phase 2.7. Amended in Phase 2.8: commission core now uses the ledger as its only financial posting path — `CommissionPoster` posts and reverses commissions through `LedgerRecorder` (ADR-018).

## Context

Commission, bonuses, adjustments and payouts will all move money. Before any of them may, the package needs one place money lives and one way it moves: exact, auditable, replay-safe and correct under concurrent writes. Nothing yet decides *why* money moves — no commission, payout, fee, tax or spending rule exists — so this foundation must not guess at any of it.

## Decision

- **The program is the financial boundary.** Wallets, accounts and transactions each belong to exactly one program, and a transaction touches accounts of its own program only. There is no tenancy abstraction.
- **A wallet is one member's money in one currency**, at most one per member and currency (`UNIQUE(program_id, member_id, currency)`). `WalletManager::open()` takes the program from the stored member, and opens the wallet together with exactly one ledger account in one transaction, or neither. Opening an open wallet returns it; a session that loses the race to open the same wallet returns the winner's.
- **Postings land on ledger accounts, never on wallets.** A wallet's account has `wallet_id` set and a key the manager derives from the wallet's id (`wallet.<id>`); a system account — a program's own, such as a future commission payable — has no wallet and a key its domain chooses, opened with `LedgerAccountManager::openSystemAccount()` and identified by program, currency and key. Keys starting with `wallet.` cannot be claimed as system accounts. The package opens no system account of its own. One posting mechanism serves both kinds, with no polymorphic target.
- **No balance is stored.** Wallets and accounts have no balance column, and there is no balance table, cache, snapshot or projection. `LedgerBalanceReader` sums an account's postings on every read; a wallet's balance is its account's. A projection may come later, with measurements and an invalidation design.
- **Signed postings, summing to zero.** A positive amount raises an account's balance, a negative one lowers it; there is no debit/credit classification yet. A transaction has at least two postings, one per account — duplicate lines are refused, not merged — none zero, and they sum to exactly zero: compared exactly, never through floats or with a tolerance.
- **One currency per transaction.** Every account of a transaction holds the transaction's currency. No cross-currency transaction or conversion exists. A currency is three uppercase ASCII letters, checked for shape only: the package ships no currency list.
- **Exact amounts.** `FinancialAmount` is its own exact decimal — Finance does not use the volume domain's quantity: six decimal places, never rounded, never a float, and no upper bound, with pure-PHP exact arithmetic. Postings are stored as signed 64-bit millionths; one posting holds at most 9,223,372,036,854.775807 **either way** — the column's negative minimum is excluded because its negation could not be stored, so every posting can be reversed. A balance, a sum of postings, may exceed 64 bits and stays exact.
- **Identity and traceability.** A transaction names its `type`, its business source (`source_type` and `source_id`, both required) and the caller's `idempotency_key`, unique within the program, and occurred at a business moment the caller gives — normalised to the application's timezone and whole seconds, never replaced by the write time. Types, source types, keys and currencies are exact machine identifiers, compared case-sensitively on every database (binary collation on MySQL). No class name, callable or code is stored.
- **Atomic posting from stored state.** `LedgerRecorder::post()` reloads the program and every account, checks each account's stored program and currency, and writes the header and all postings in one transaction — a savepoint inside a caller's — with one write timestamp: all of it, or nothing. Models changed in memory cannot redirect it.
- **Idempotent replay.** A request under a key already used returns the stored transaction if it matches in currency, type, source, moment, reversal and postings — compared per account, whatever the order the lines were given in — and is refused with `ConflictingLedgerReplay` otherwise. The unique keys are the concurrency backstop: two identical racing posts give one transaction, and a conflicting one is refused as a conflict, not as a raw constraint error.
- **Corrections are reversals.** `LedgerRecorder::reverse()` appends a new transaction in the same program, currency and type, on the same accounts, with every posting negated, under its own source, key and moment, and `reversal_of_id` naming the original. It takes no amounts from the caller. The original is never updated or deleted. A transaction is reversed at most once (`UNIQUE(reversal_of_id)`), a reversal is not reversed, and a racing second reversal is refused as already reversed. Balances need no special case: the reversal's postings net the original's.
- **Immutable history.** Wallets, accounts, transactions and postings are read-only through Eloquent — creating, updating or deleting one through a model is refused — and every foreign key restricts deletion. Raw query-builder writes bypass these guards and are not a supported way to keep the ledger's invariants; readers refuse the ambiguous states they can detect, such as a wallet without its account.
- **Negative balances are allowed.** The ledger sets no floor, overdraft rule or available/pending split: whether a balance may be spent below zero is a business rule for the domains that spend it.
- **Nothing else yet.** No transfer, deposit, withdrawal or payment API, no pending or reserved buckets, no tax, fee or rounding policy, no commission and no payout. Future domains post through `LedgerRecorder::post()`.

## Consequences

- Every future financial result has one exact, balanced, replay-safe, auditable destination, and every balance can be recomputed from history.
- A balance read costs a scan of the account's postings, read in chunks and summed in PHP: SQLite's integer `SUM` overflows past 64 bits, so the database is not asked to sum. A read concurrent with posting includes every transaction committed before it began, and may include some committed during it. A projection is the later optimisation, once measured.
- On MySQL, a caller's REPEATABLE READ transaction reads from a snapshot taken at its first read. After losing a race inside such a transaction, the recorder and the wallet manager re-read the winner's rows with locking reads: the header and `reversal_of_id` lookups are exact unique-key reads, which lock only the rows they find. A winner's postings are re-read with a locking read only when a plain read sees none — a stored transaction always has postings — and an account missing from a plain read is re-read the same way. That locking read of postings covers an index range, so it can hold next-key locks until the caller's transaction ends; it happens only on this path. Plain reads a caller makes later in the same transaction still see its snapshot.
- Deciding what money means — commission lifecycle, payable and clearing accounts, payouts, spending rules, fees and rounding — belongs to later phases, which build on this ledger rather than beside it.
