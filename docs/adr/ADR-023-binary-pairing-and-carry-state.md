# ADR-023: Binary pairing keeps source-level carry, committed with its run under serializable isolation

## Status

Accepted — Phase 3.3. Amended in Phase 3.4B: a reversal of carry that was already paired no longer stops the run; the pairs it fed are undone and the other side's carry given back (ADR-025), and results record `left_restored`/`right_restored`. Completed in Phase 3.4C: the commissions of undone pairs are corrected financially (ADR-026) — binary structure, pairing, carry, consumed-source reversal and financial correction are complete.

## Context

A binary plan pays when both legs of a member (ADR-022) have brought business: an equal quantity is taken from each leg to form a pair, and whatever cannot pair yet is carried to the next period. That makes the calculation stateful — each run depends on what earlier runs left — while the commission core (ADR-018) was built for stateless strategies that read and return candidates. Carry must also stay explainable: a sale that is refunded later has to be traceable to the pairs it fed, so a carry balance of two numbers is not enough.

## Decision

- **A generic, additive stateful extension.** `StatefulCommissionStrategy` extends `CommissionStrategy` with `calculateStateful()`, which returns a `StatefulCommissionCalculation`: the candidates and a `CommissionStateTransition`. The transition is data — what the calculation decided, planned from what it read — and `apply(Connection, CalculationRun)` writes it. Existing strategies, the package's and applications', are untouched. The calculation context also names the stored component calculated (`planComponentId`), the identity state is kept under.
- **Atomic with the run.** For a stateful strategy the engine checks every candidate, stores the run and its commissions, then applies the transition, in one transaction: a transition that fails keeps no run, no commission and no state. A replay under a stored key returns the stored run and neither calculates nor applies anything. The engine knows no strategy's tables or keys: only the interface.
- **Serializable, and retried.** Two runs of one component must never consume the same carry, so stateful runs use `StatefulCalculationTransaction`: SERIALIZABLE on MySQL, MariaDB and PostgreSQL (set for that transaction only), a plain transaction on SQLite, which lets one writer commit at a time. An attempt the database refuses — a deadlock or serialization failure as Laravel's own concurrency detection recognises it, or a unique key another run took first — is rolled back and run again from its first read, at most five times. So a stateful calculation must stay read-only and deterministic: no writes, clock, randomness, events or network. Each attempt first looks for a run already stored under its key, so a run that waited for its own twin replays it.
- **Stateless runs keep their snapshot.** The four existing strategies, and any other stateless one, still calculate under `ReadSnapshot` (REPEATABLE READ): serializable isolation is paid only where state demands it.
- **`binary.pairing.fixed` and `binary.pairing.proportional`.** Both take exactly `volume_type` (the volume type that feeds the legs, checked as volume checks it), `pair_quantity` (an exact, strictly positive quantity of at most six decimals — the quantity one pair takes from each leg) and their award: `amount_per_pair` (a strictly positive amount that fits one posting) for the fixed strategy, or `unit_amount` and `rounding` (ADR-020) for the proportional one. No rules: a rule is refused, not ignored. Both are registered like every built-in strategy and validated through the `commission.strategy` component.
- **Pairing at the run's close.** A run first takes in everything in its range, then pairs once per binary member: available = carry before + added − taken back, on each side; pairs = ⌊min(left, right) ÷ pair quantity⌋ — an exact whole number of any size; consumed = pairs × pair quantity, taken from both sides alike; carry after = available − consumed. All exact, in decimal digits: no float, no 64-bit limit. Pairing does not depend on the order entries are read in.
- **The award.** Fixed: pairs × `amount_per_pair`, exactly — a whole multiple, never rounded. Proportional: the consumed quantity × `unit_amount`, rounded once by the configured mode, through the same calculator as every proportional award. One commission at most per binary member and run, keyed `binary-pairing:<member>`, earned at the run's `until` — the settlement boundary, not any one entry's moment. An award larger than one posting fails the whole run and nothing moves. A proportional award that rounds to nothing earns no commission, but the pairs still formed and still consumed carry: the result records them.
- **No single source.** A pairing commission is earned from many entries on both legs, so it has no `volume-entry` provenance (ADR-021): its sources are its allocations. Its trace explains the calculation in totals — pairs, carry before and after on each side, the award — never every source.
- **State per component, in contiguous runs.** A cursor per plan component records where its state began and how far it has calculated. The first run starts it at its `from`; earlier activity is outside this component's history. Every later run must start exactly at the cursor: an overlap, or the same range under a new key, is refused as stale, a gap as a gap (`InvalidBinaryPairingRange`), and the cursor moves only when a run commits. Because state belongs to the component's id, a new plan version — a new component — starts with no carry, and the old version's component keeps its own and can still be calculated. Nothing carries over between versions automatically: whether it should is a plan decision to make explicitly, later.
- **Carry by source.** Carry is kept as lots: one original entry, as it fell in one side of one binary member's legs, for one component — its quantity (one entry's, so one BIGINT holds it) and what remains unpaired. The side is the one the binary tree gave it at the entry's own moment, attributed exactly as the leg metrics attribute (ADR-022) — never by the current tree, generic placement or sponsorship — and never changes. A member's own activity is never in its own legs. Lots are found set-based: a chunk of entries at a time, one query over the binary paths and positions per chunk, never a query per entry or ancestor. A member's carry is the sum of its open lots, added exactly in the package — no aggregate balance is stored, and no database sum can overflow it.
- **FIFO, recorded.** Pairs consume each side's carry oldest source first — by the source's moment, then its entry id — so earlier runs' lots before this run's. Every draw is an allocation: this result took so much of that lot. A result per run and binary member — whenever it had carry, or anything was added, taken back or paired — records carry before, added, taken back, available, the pairs, the consumed quantity, carry after, and its commission, as exact decimal text of any size. Results and allocations are written once; lots and cursor change only through the transition, which checks first that they are still as the calculation read them.
- **Reversals.** A reversal belongs to the run its own moment falls in, and reaches the lots of its original's moment. An original reversed before its run ends — in the same run, or at an earlier moment — is taken in and taken back at once: it never pairs. A reversal of an original an earlier run took in takes its lots back while they are wholly unpaired. If any of it was already paired, the run stops with `BinaryPairingCorrectionRequired`, naming the component, member, side, entry, paired quantity and reversal, and keeps nothing: rewriting a pair that has earned a commission needs an explicit correction, not a quiet negative carry. A reversal of activity before the component's state began is not its concern.

- **Indexes from measurement.** Besides the keys, lots are indexed by source entry (a reversal finds its lots), and for open carry: by member and side, and — covering what a run reads — by component. Measured on MySQL 9.6 over an 8,191-member binary tree, reading carry in source order walked past every lot ever consumed: 2.1 s to sum 25,142 open lots among 275,177, and 96 ms to reach one busy member's side. With the open-carry indexes, 25–35 ms and about 1 ms, whatever the consumed history.

## Consequences

- Binary plans pay on legs with exact, explainable carry: every commission leads through its allocations and lots to the entries it was paid on — the provenance a later correction will need.
- A consumed source's reversal blocks the component's next run until a correction exists; clawing back binary commissions is the next design.
- Runs of a component must be calculated in order, without gaps. Volume recorded later with a moment in an already-calculated range is not taken in by that component.
- Stateful runs cost serializable isolation and, under contention, retries; MySQL takes shared locks on what they read for their duration.
- Carry expiry, pair caps, carry between plan versions and qualification of recipients remain later designs.
