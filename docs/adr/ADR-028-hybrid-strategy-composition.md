# ADR-028: Hybrid compensation composes a plan version's commission components as one resumable, idempotent batch of their own runs

## Status

Accepted — Phase 3.6.

## Context

Real plans pay through several structures at once — a binary pairing bonus, a matrix override and a unilevel bonus in one plan. Each already exists as a commission component calculated by `CalculationEngine` (ADR-018), and some keep state under their own serializable transaction (ADR-023). Paying them together needs one auditable request, safe to retry, whose money never moves half-way — without a new genealogy, a strategy that knows every network, or a transaction wrapped around every component.

## Decision

- **Composition at the plan version.** A hybrid is a plan version with two or more `commission.strategy` components; they are the composition, by `position`, then `id`. Its other components — a rank ladder — belong to their own engines and are not calculated. A version with one commission component is calculated with `CalculationEngine`, and a version with none is refused (`InvalidHybridCalculation`). Validated versions are immutable (ADR-005), so the composition cannot change under a batch; a cloned version is a new composition with no batch, run or state of its own.
- **No hybrid genealogy, strategy or state.** There is no hybrid tree, metric, strategy registry key, carry, wallet or ledger. Each component is calculated by its own strategy through its own network; none reads another's result, and cross-component rules — matching, caps, "the greater of" — are later designs.
- **`HybridCalculationEngine::calculate(PlanVersion, CalculationContext, LedgerAccount)`.** One range [from, until), one idempotency key and one source account for every component. The account must be a system account of the plan's program, and every component must be funded from it — its own `source_account` and currency — or nothing is created.
- **A batch, and an item per component.** `mlm_calculation_batches` holds the request — program, plan version, source account, range, key (`UNIQUE(program_id, idempotency_key)`) — and its status, `open` then `completed`. `mlm_calculation_batch_items` holds one row per component, positions 1, 2, 3… in the canonical order, with the key its run is calculated under, `hybrid:<batch>:<component>`, and — once calculated — that run (`UNIQUE`, nullable). Items are written with the batch; only the run is linked later, once, never replaced. Runs keep no batch column: a run calculated on its own stays standalone, and no existing run is gathered into a batch. Both models are read-only through Eloquent; batch, items, runs and commissions answer what was calculated, in what order and from what, relationally.
- **Each component through `CalculationEngine`, unchanged.** Strategy lookup, validation, the read snapshot or the serializable transaction and its retries, state transitions and replay are the engine's. Transitions are never combined.
- **Not one transaction.** Opening the batch is one short transaction under the program's lock — taken before anything else is read in it — and linking each run and completing the batch are short transactions of their own. Each component commits its own run. A component that fails leaves the batch `open` and the runs before it standing: they are valid calculations.
- **Resume, replay, recovery.** The same request again resumes an open batch: linked runs are kept (checked to be their component's run, under its key, over the batch's range and account), and the rest are calculated under their keys — so a run committed before a crash could link it is returned by the engine's own replay and linked, with no repair step. A batch is `completed` once every item is linked; a completed batch is returned as stored, with nothing calculated or written. The same key with another plan version, range or source account is refused (`ConflictingCalculationBatch`); items that are not exactly the version's commission components, or a link to another run, are refused as corrupt (`CorruptCalculationBatch`). Another key is another request: a stateful component refuses a range it has already calculated (ADR-023), and that batch stays open.
- **Concurrency.** Two identical requests serialize on the program's row to open one batch, then calculate under the same keys: the engine's idempotency leaves one run per component and state moved once, and both resolve the same completed batch. A conflicting request under the same key is refused before calculating anything.
- **No money moves from an open batch.** `CommissionPoster::post()` refuses a commission whose run belongs to an open batch (`IncompleteCalculationBatch`) — linked to an item, or calculated under an item's key before the link was written. Once completed, posting is exactly as before, binary correction guard and net amount included (ADR-026); standalone runs post as ever. The commission lifecycle is unchanged: batch status is orchestration, not a commission status.
- **Commissions stay apart.** Every component's commissions are its run's: two components paying one member make two commissions, and candidate keys are unique per run, not per batch. Nothing is merged, netted or aggregated.
- **Corrections stay with their domains.** A source reversal is corrected by `processVolumeReversal()` for source-entry commissions (ADR-021) and by the binary correction and `processBinaryReversal()` for pairing commissions (ADR-025, ADR-026). There is no hybrid reversal.

## Consequences

- Plans combining binary, matrix, unilevel and direct-sponsor components are calculated and audited as one request, safely retried after a failure, and paid only once complete.
- Every component of a hybrid version is funded from one source account; components funded differently are calculated separately.
- Cross-component formulas and caps, matching, generation, pool, leadership and fast-start bonuses, recipient qualification, calculation periods, batch approval and payouts remain later designs.
