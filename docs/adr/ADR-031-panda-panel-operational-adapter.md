# ADR-031: The Panda Panel surface is an adapter over the domain services

## Status

Accepted — Phase 3.9A; completed in Phase 3.9B.

## Context

Every MLM domain up to payouts (ADR-030) is written and read through package services, with no operator screen. Operators need to see programs, members, plans, periods, runs, commissions, wallets, the ledger and payouts, and to move periods and payouts through their lifecycles — without the screens becoming a second place where business rules live, and without the domain depending on an admin framework. The package already declared `PandaMlmPlugin` for Panda Panel (`chocoalano/panel` ^0.5.7), registering nothing.

## Decision

- **Adapter only.** Everything Panda Panel-specific lives under `PandaBear\Mlm\Panel` and in `PandaMlmPlugin`. Resources read the domain's models; every lifecycle action is one call to a domain service. No resource, page, table, action or widget restates an invariant: an action is *offered* in the status its step starts from, using the domain's own status enums (`canTransitionTo()`), but whether the step may happen is the service's answer under its own locks. The domain namespaces never import `PandaPanel\`; a test holds this.
- **Registration.** `register()` adds ten resources and two pages (the overview and the genealogy explorer) through `Panel::resources()` and `Panel::pages()` — classes only, nothing queried. `boot()` and `publishes()` stay empty: the surface uses the panel's own components, translations load from the package under the `mlm` namespace (`lang/vendor/mlm` overrides them), and no Vue is shipped. Slugs are prefixed `mlm-` so they cannot collide with an application's own resources. The overview widget belongs to the overview page, not to the panel's widget registry, so it never lands on an application's own dashboard.
- **Program is the business boundary.** No tenant, tenant scope or workspace selector. The overview is global across what the operator may see; program detail lives on the program page.
- **Capabilities, not roles.** `MlmPermission` names eighteen Gate abilities: eleven `view` (`mlm.dashboard.view`, `mlm.programs.view`, `mlm.members.view`, `mlm.network.view`, `mlm.plans.view`, `mlm.periods.view`, `mlm.calculations.view`, `mlm.commissions.view`, `mlm.wallets.view`, `mlm.ledger.view`, `mlm.payouts.view`) and seven `operate` (`mlm.programs.operate`, `mlm.members.operate`, `mlm.network.operate`, `mlm.plans.operate`, `mlm.periods.operate`, `mlm.commissions.operate`, `mlm.payouts.operate`), each governing its own area's actions and no other. Every action asks its capability twice: the panel before running it, and the handler itself before calling its service — a request that reaches a handler another way is still refused. Resources and relation managers override the panel's `can*` methods to ask them; no policy is registered for a domain model and no role is ever named. Panda Panel has no permission discovery, so the catalogue is exposed as `MlmPermission::all()` and `PandaMlmPlugin::permissions()`.
- **No generic writes.** Programs, members, plans, plan versions, commission periods, calculation runs, commissions, wallets, payout requests and payout batches register only `index` and `view` pages. Every create, edit, delete, restore, attach, detach, associate and dissociate ability the panel offers generically answers no, on every resource and relation manager — financial and audit records are never deleted, and no status is ever a form field. Records are created by explicit actions whose handlers call a service: `ProgramManager` (programs, members, plans), `CommissionPeriodManager`, `PayoutManager::request()`, `PayoutBatchManager::create()` and `add()`, `LedgerAccountManager::openSystemAccount()`. The ledger is reached from wallets (postings), commissions and payout requests (transaction references), behind `mlm.ledger.view`.
- **Lifecycle actions call services.** Commission: `Mark pending`, `Approve`, `Cancel` → `CommissionLifecycle`; `Post` → `CommissionPoster`, the one step here that moves money. Period: `Calculate` → `CommissionPeriodCalculator` (never the calculation engines beneath it), `Finalize` → `CommissionPeriodFinalizer`, `Release` → `CommissionPeriodReleaser` with an operator-stated moment. Payout request: `Approve`, `Start processing`, `Settle` (reference and moment), `Mark failed` (reason and moment), `Cancel` (optional reason) → `PayoutManager`. Payout batch: `Seal`, `Start processing`, `Complete`, `Cancel batch` → `PayoutBatchManager`. Each confirmation says whether money moves. Each action opts out of the panel's own database transaction: the services own theirs, and the period calculator refuses to run inside a caller's.
- **The Plan Builder is the plan version page.** Its overview, components and rules tables and a review of the whole stored definition, with component and rule edits through `PlanDefinitionEditor` while the version is a draft, and validate, publish, activate, archive and clone through `PlanVersionLifecycle` and `PlanDefinitionCloner`. Drivers, strategies, metrics and operators are chosen from their registries and enums, so an unregistered key is refused by the form's own whitelist; a built-in strategy's parameters are the fields its parameter class names; anything else is a decoded JSON object, stored as data. `PlanDefinitionValidator` alone decides whether a definition is valid. A wizard was not used: the builder edits a stored draft step by step rather than submitting a whole definition at once.
- **Networks are written from the member.** Sponsor, generic placement, binary and matrix placement and adoption, and the matrix width, each one service call with the parent and side or slot chosen explicitly; nothing moves, removes or places automatically, and the services refuse cross-program, cyclic, occupied and out-of-range requests. A record choice is validated as a real row (`existsIn`, on the MLM connection) rather than as one of the options shown, so the service — not the form — refuses a member of another program.
- **The genealogy explorer is bounded and Panda-native.** A page with filters (program, anchor code, network, as-of moment, depth 1–5) and two widgets. It counts the anchor's closure paths first (`ClosureTree::countDescendants()`, the reader's own filter, counted) and loads only the deepest level that stays within 500 members, through the network's genealogy reader — `descendants()` now, `descendantsAt()` as of a moment — plus one query for the direct links; no read is per node, and nothing is written. Panda Panel resolves Vue components only from the application's own tree, and a plugin can only deliver one by publishing it into the application's build, which this package cannot build or check. So the explorer draws the tree with the panel's table — order and indentation carry the hierarchy — and ships no Vue.
- **Refusals reach the operator.** An expected domain refusal (`InvalidCommissionPeriodTransition`, `InvalidPayoutTransition`, `InsufficientPayoutBalance`, `InvalidPayoutBatch`, …) becomes a redirect back with the panel's error toast carrying the service's reason. Corruption and unexpected failures are not caught.
- **Reads stay set-based.** Counts, parent codes and the latest period are aggregates or correlated subqueries of the list query; a wallet's balance comes from `LedgerBalanceReader::forWallets()` — the same exact, chunked, PHP-side sum as `forWallet()`, one read per page rather than one per row, never a stored column. Derived columns are not sortable, searchable or offered as query conditions. The overview shows four counts, never an amount summed across currencies.
- **Operator language.** Every visible word is in English and Indonesian. A period that is open with its input closed — a calculation attempt that did not finish — is shown as its own warning state, not as an ordinary open period.

## Consequences

- An application installs the plugin, grants capabilities as it grants any ability, and gets the operational surface; removing the plugin changes nothing in the domain.
- An operator can configure and operate everything the engine implements without editing a database row: programs, members, system accounts, plans and their versions, the four networks, periods and their lifecycle, commission review and posting, and payouts from request to settlement.
- Panda Panel findings: a view page always links to its resource's index, so the plan-version resource keeps a list page, out of the sidebar; `panel:icons` scans the application and the framework but not plugins, so the surface uses only icons the framework already declares; the panel wraps actions in a transaction by default, which the domain services must be released from; an action hidden for a record can still be posted, so handlers and services decide; a relation manager's record lookup over a `HasManyThrough` selects every joined column, so the rules table narrows it to the rules' own; a static select whitelists only the options it shows; and a plugin cannot ship a Vue component without publishing it into the application.
- Not in Phase 3.9: moving or removing any network position, automatic placement and spillover, nested rule groups in the builder's form, bulk commission review, and a plugin-shipped visual tree.
- Phase 3.9 is complete.
