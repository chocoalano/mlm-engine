# ADR-031: The Panda Panel surface is an adapter over the domain services

## Status

Accepted — Phase 3.9A.

## Context

Every MLM domain up to payouts (ADR-030) is written and read through package services, with no operator screen. Operators need to see programs, members, plans, periods, runs, commissions, wallets, the ledger and payouts, and to move periods and payouts through their lifecycles — without the screens becoming a second place where business rules live, and without the domain depending on an admin framework. The package already declared `PandaMlmPlugin` for Panda Panel (`chocoalano/panel` ^0.5.7), registering nothing.

## Decision

- **Adapter only.** Everything Panda Panel-specific lives under `PandaBear\Mlm\Panel` and in `PandaMlmPlugin`. Resources read the domain's models; every lifecycle action is one call to a domain service. No resource, page, table, action or widget restates an invariant: an action is *offered* in the status its step starts from, using the domain's own status enums (`canTransitionTo()`), but whether the step may happen is the service's answer under its own locks. The domain namespaces never import `PandaPanel\`; a test holds this.
- **Registration.** `register()` adds ten resources and one page through `Panel::resources()` and `Panel::pages()` — classes only, nothing queried. `boot()` and `publishes()` stay empty: the surface uses the panel's own components, translations load from the package under the `mlm` namespace (`lang/vendor/mlm` overrides them), and no Vue is shipped. Slugs are prefixed `mlm-` so they cannot collide with an application's own resources. The overview widget belongs to the overview page, not to the panel's widget registry, so it never lands on an application's own dashboard.
- **Program is the business boundary.** No tenant, tenant scope or workspace selector. The overview is global across what the operator may see; program detail lives on the program page.
- **Capabilities, not roles.** `MlmPermission` names twelve Gate abilities: ten `view` (`mlm.dashboard.view`, `mlm.programs.view`, `mlm.members.view`, `mlm.plans.view`, `mlm.periods.view`, `mlm.calculations.view`, `mlm.commissions.view`, `mlm.wallets.view`, `mlm.ledger.view`, `mlm.payouts.view`) and two `operate` (`mlm.periods.operate`, `mlm.payouts.operate`). Resources and relation managers override the panel's `can*` methods to ask them; no policy is registered for a domain model and no role is ever named. Panda Panel has no permission discovery, so the catalogue is exposed as `MlmPermission::all()` and `PandaMlmPlugin::permissions()`.
- **Read-oriented resources.** Programs, members, plans (with a plan-version detail), commission periods, calculation runs, commissions, wallets, payout requests and payout batches register only `index` and `view` pages. Every create, edit, delete, restore, attach, detach, associate and dissociate ability answers no, on every resource and relation manager — financial and audit records are never deleted, and no status is ever a form field. The ledger is reached from wallets (postings), commissions and payout requests (transaction references), behind `mlm.ledger.view`.
- **Lifecycle actions call services.** Period: `Calculate` → `CommissionPeriodCalculator` (never the calculation engines beneath it), `Finalize` → `CommissionPeriodFinalizer`, `Release` → `CommissionPeriodReleaser` with an operator-stated moment. Payout request: `Approve`, `Start processing`, `Settle` (reference and moment), `Mark failed` (reason and moment), `Cancel` (optional reason) → `PayoutManager`. Payout batch: `Seal`, `Start processing`, `Complete`, `Cancel batch` → `PayoutBatchManager`. Each confirmation says whether money moves. Each action opts out of the panel's own database transaction: the services own theirs, and the period calculator refuses to run inside a caller's.
- **Refusals reach the operator.** An expected domain refusal (`InvalidCommissionPeriodTransition`, `InvalidPayoutTransition`, `InsufficientPayoutBalance`, `InvalidPayoutBatch`, …) becomes a redirect back with the panel's error toast carrying the service's reason. Corruption and unexpected failures are not caught.
- **Reads stay set-based.** Counts, parent codes and the latest period are aggregates or correlated subqueries of the list query; a wallet's balance comes from `LedgerBalanceReader::forWallets()` — the same exact, chunked, PHP-side sum as `forWallet()`, one read per page rather than one per row, never a stored column. Derived columns are not sortable, searchable or offered as query conditions. The overview shows four counts, never an amount summed across currencies.
- **Operator language.** Every visible word is in English and Indonesian. A period that is open with its input closed — a calculation attempt that did not finish — is shown as its own warning state, not as an ordinary open period.

## Consequences

- An application installs the plugin, grants capabilities as it grants any ability, and gets the operational surface; removing the plugin changes nothing in the domain.
- Panda Panel findings: a view page always links to its resource's index, so the plan-version resource keeps a list page, out of the sidebar; `panel:icons` scans the application and the framework but not plugins, so the surface uses only icons the framework already declares; the panel wraps actions in a transaction by default, which the domain services must be released from.
- Phase 3.9B: the Plan Builder; program and member creation; sponsor, placement, binary and matrix assignment; genealogy visualisation; payout request creation and batch composition; and the final Phase 3.9 database gate.
